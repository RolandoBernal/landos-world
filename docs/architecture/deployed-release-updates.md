# Deployed Release Updates

## Identity

Production deployment metadata is generated by `scripts/build-pages.mjs` in the GitHub Pages Actions workflow. `deployment-version.json` is the network-checked representation; the same metadata is embedded in `js/landos-world-build-metadata.js`, which is part of the application shell. Both identify the exact full Git commit SHA, a short SHA for diagnostics, a readable release label, workflow run number, and build timestamp.

The release label is the deployed commit's UTC committer date plus the GitHub Actions run number for this workflow (`YYYY-MM-DD-N`). Both inputs are stable for a workflow retry; the run number is monotonically assigned per workflow. A deliberate new deployment run of the same commit gets a new run number and can produce a different display label; the full commit SHA is authoritative, so equal SHAs are still Up to date and do not prompt. The label is for people, not comparison. `builtAt` separately records the actual UTC artifact-build time.

`SW_VERSION` is injected from the complete SHA and remains an internal cache namespace. The worker's `commit` and `shortCommit`, the page metadata, and `deployment-version.json` use the same seven-character short SHA; all running/latest comparisons and worker verification use the complete SHA. This release identity is unrelated to Lee-Lee's Tracker shared Supabase settings version or per-record `appVersion` data.

## Freshness and offline behavior

The page appends a unique query value to `deployment-version.json` and requests it with `cache: 'no-store'`. The service worker has a dedicated network-only route for this endpoint before all cache strategies and never writes the response to Cache Storage. A request error, invalid JSON, unsupported network state, or missing fields results in Unknown / Unverified; a previously cached endpoint response cannot be used to assert current status.

The page checks on startup, foreground/pageshow, reconnect, and at the existing 15-minute active-session interval. There is no fast/aggressive polling. Latest-version failure does not affect app-shell launch or offline data.

## User-controlled activation

Updated workers precache the matching build metadata and app shell, then wait. Update Now refreshes the worker registration, verifies the waiting worker's full SHA against the latest deployed metadata, requests `SKIP_WAITING`, and waits for `controllerchange` plus a matching worker SHA before reloading. The new page compares its embedded SHA to the one-shot session reload marker; a mismatch is reported and is never retried automatically.

Later suppresses the current SHA's notice until an appropriate later foreground/reopen check. A new different production SHA can still be shown. No update is automatic.

The PWA manager exposes `LandosPWA.registerUpdateBlocker(name, callback)` and `LandosPWA.notifyUpdateSafetyChanged()`. A callback returns `false`/an empty value when reload is safe, `true` or a message while work must be protected, and should be synchronous. A callback exception fails closed. Ordinary form presence or focus does not imply unsaved work and does not block updates. An app with meaningful transient work must explicitly register its safety condition and call `notifyUpdateSafetyChanged()` as that condition changes. A deferred update or restart proceeds after the blocker clears only when that action was explicitly requested by the user first.

If a different worker build begins controlling a page (for example, after the legacy updater's waiting-worker flow activates a newly deployed worker), the manager compares that worker's embedded full SHA to the page's running SHA. Only the tab that initiated Update Now reloads as part of that action. Other controlled tabs show a persistent Restart This Tab action rather than reloading automatically; explicit blockers still prevent reload, and a restart that the user already requested can finish when the blocker clears. A session marker prevents the same build from triggering a repeated reload loop.

The one-time first deployment has a legacy-client limitation: old page JavaScript cannot compare worker/page SHAs because it predates build identity. Its existing Update Available → Restart control does send the compatible `SKIP_WAITING` message and reloads the initiating tab on `controllerchange`. Since the new worker calls `clients.claim()`, other already-open legacy tabs could be controlled without understanding the new build. For the first release-aware deployment only, close all other Lando's World tabs/windows before using Restart, then verify the newly loaded page reports the deployed SHA and Up to date. Once release-aware page code is loaded, the multi-client mismatch policy above applies.

## GitHub Pages migration

`.github/workflows/pages.yml` deploys only `main` pushes and manual runs targeting `main`. `scripts/pages-runtime-allowlist.mjs` explicitly enumerates every static site asset copied into the Pages artifact; tests, docs, server functions, repository metadata, and other developer files are excluded. The builder verifies that every service-worker precache URL resolves to a regular file in the artifact before upload. Generated release metadata and `.nojekyll` are written only into the staged artifact. Before enabling this workflow, an administrator must change **Repository Settings → Pages → Build and deployment → Source** from **Deploy from a branch** to **GitHub Actions**. This repository setting is deliberately not changed by code in this repository.

The artifact build copies only the reviewed runtime allowlist, then writes generated metadata into the staged copy. It does not add generated production metadata to the source checkout, package or clear browser data, or publish untracked local reports.
